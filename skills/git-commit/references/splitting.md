# 何时拆分提交

## 三个判据

一个提交应该满足：

1. **只表达一个意图**——能用一句话说清，且不需要"顺便"这个词
2. **能独立回滚**——撤销它不会连带撤掉无关功能
3. **能独立 review**——评审者不需要在多个主题之间来回跳

## 必须拆分的情况

| 情况 | 原因 |
| --- | --- |
| 功能代码 + 全仓库格式化 | 格式化会淹没真实改动，review 无法进行 |
| 重构 + 新增功能 | 出问题时无法判断是重构引入还是新功能引入 |
| 两个不相关模块的改动 | 回滚其中一个会牵连另一个 |
| 修复 bug + 升级依赖 | 依赖升级可能是 bug 的来源，混在一起无法二分定位 |

## 不必拆分的情况

- 一个功能涉及多个文件（接口、实现、样式）
- 代码改动与对应测试
- 代码改动与相关文档
- 一次重命名涉及的所有引用点

判断标准是"意图是否唯一"，不是"文件是否唯一"。

## 怎么拆

### 按文件拆

```bash
git add src/login.js src/login.test.js
# 提交这一组
git add src/cart.js
# 提交另一组
```

### 按 hunk 拆

同一文件里的两类改动，用交互式暂存：

```bash
git add -p src/service.js
# y 暂存本块，n 跳过，s 再切分，e 手动编辑
```

### 拆完之后

每一组都完整走一遍流程：生成信息 → 校验 → 确认 → 提交。不要先生成一条大信息再硬拆。

## 反例

一次提交里同时出现：

```
feat: 新增导出功能并修复登录超时并升级依赖
```

这条信息本身就是拆分信号：出现了两个"并"。
